**Память проекта для [oh-my-pi (OMP)](https://github.com/can1357/oh-my-pi): что решили, почему, где искать и что осталось сделать.**

После перезапуска агент получает сохранённые знания о проекте. Текущее состояние лежит в читаемых файлах, история и свидетельства — в локальной SQLite. Расширение помогает отличать подтверждённые решения от предположений и замечать устаревшие записи.

Один плагин. Без отдельного сервера, embeddings и фоновой нейросети. Работает с основной моделью OMP, в том числе локальной.

> **Предварительная версия 0.8.3.** Проверена с OMP 18.11.0. Обычный Pi пока не поддерживается. Плагин помогает восстановить и проверить контекст; отсутствие галлюцинаций не гарантирует.

## Для кого

Для разработчиков, которые ведут проект с ИИ и не хотят в каждой сессии заново объяснять архитектуру. Особенно полезно, если основная локальная модель занимает доступные ресурсы и запускать дополнительную модель ради памяти неудобно.

## Что даёт

- **Знания рядом с кодом.** Факты, решения и задачи можно открыть, исправить и хранить в Git.
- **Источник у записи.** Реестр проверяет цитату пользователя или содержимое файла. ID сообщения и хеш вычисляет код.
- **Историю исправлений.** Новое решение получает следующую версию записи. Старое остаётся в истории.
- **Видимое устаревание.** Изменился источник или основные документы — запись получает `STALE` и требует проверки.
- **Ограниченный контекст.** Расширение передаёт блок до 9000 символов: правила, список канонических файлов и записи по вопросу. Полные источники агент читает по необходимости.

## Установка

**Новое в 0.8.3 — честные роли запросов и меньше чтений по страницам:**

- Запросы, созданные самой средой, — одобрение плана OMP (роль `developer`), synthetic- или
  agent-сообщения — сохраняются как текст ассистента и не могут служить `origin=user` или
  основанием принятого решения. OMP 18.11 добавляет сообщение запроса после `before_agent_start`,
  поэтому роль определяется при сборке первого запроса к модели. Если сообщение не видно,
  запрос остаётся пользовательским, как раньше. Сохранённые прежними версиями сообщения не переразмечаются.
- `episodes id=<id>` учитывает `limit=<единицы UTF-16>`: от 200 до 12 000 на страницу вместо
  фиксированных 2400. Поиск учитывает `limit` от 1 до 10 совпадений. Поле было в схеме, но игнорировалось.
- Публикация Wiki больше не создаёт `.memory/wiki/.<id>.lock`: после аварии такой файл давал
  вечный `WIKI_CONFLICT`. Публикации упорядочивает immediate-транзакция записи базы области;
  оставшийся от 0.7.0–0.8.2 файл блокировки игнорируется, его можно удалить.
- Schema 2 и форматы записей не меняются.

**Новое в 0.8.2 — корректное завершение и меньше повторной работы:**

- `/huimem learn` ждёт окончания native recovery OMP, сохраняя привязку пакета.
  Прерывание освобождает команду; незавершённый разбор не подтверждается.
- Ошибка аргумента не объявляет хранилище неисправным из-за слова `database` в ID.
  Настоящие ошибки SQLite и файлового ввода-вывода по-прежнему меняют состояние здоровья.
- Wiki read/list/lint используют общие проверки только внутри одного SQLite read snapshot.
  Следующая операция снова проверяет источники; независимые проверки публикации сохранены.
  TTL и замороженной «истины» нет.
- Индекс роли/времени ускоряет прежнюю дедупликацию в её временном окне.
  Schema 2, одиннадцать таблиц, исходные сообщения и `WAL/FULL` не меняются.
- Новые захваты маскируют распознаваемые GitHub/Slack token, AWS access-key ID,
  блоки приватных ключей и пароли credential-URL. Новая запись не копирует секрет из
  цитаты старого сообщения: используйте точный несекретный отрывок.
  Старая история не переписывается. Эвристический фильтр не заменяет хранилище секретов.

**Единый цикл «источник → запись → Wiki» с 0.8.0, уточнённый в 0.8.1:**

- **Возобновляемый разбор.** `project_memory op=learn action=next` выдаёт старейший
  необработанный пакет: до 12000 UTF-16 единиц и восьми источников, с исходными ролями,
  точным текстом и смещениями. Чтение ничего не подтверждает. Только проверенный `complete`
  продвигает покрытие; прерывание оставляет работу в очереди, одинаковый повтор ничего не пишет.
- **Без второй модели.** `/huimem learn` сам читает ограниченный пакет до запуска
  основного агента и передаёт точные ID, роли и текст — модели не нужно искать эти адреса.
  Opaque token подтверждения остаётся в runtime: модель завершает выданный пакет, не перепечатывая
  его fingerprint. Повреждённое состояние останавливает команду до модельного хода. Агент
  обновляет прежние ID, сохраняет полезные процедуры и оформляет Wiki до однократного
  подтверждения. `/huimem learn status` работает без LLM. Обязательные правила контролирует
  человек; предположение ассистента и отметка «просмотрено» не становятся фактом.
- **Wiki-workbench.** `op=wiki action=plan` разделяет подтверждённые записи без актуальной
  страницы, устаревшие страницы, предложения для проверки и кандидатов с одинаковым текстом.
  `action=discover id=<page>` раскрывает общие источники, связи/зависимости и обратные ссылки
  из существующего графа записей, не выдумывая сущности по тексту.
- **Одна истина, прежнее хранилище.** Наблюдения — обычные версионированные записи,
  обобщения — производная Wiki. Курсор и receipts лежат в namespaced meta schema 2, без
  новых таблиц и второй стенограммы. Настоящие bundle 0.6.10 и 0.7.0 читают и дописывают
  данные после обновления/отката; формат прежних Wiki-страниц сохранён.

[Аудит закреплённых исходников](../RETRIEVAL-RESEARCH.md#unified-cycle-080) объясняет
выбор механизмов Hermes, Observational Memory и LLM Wiki. Фоновых observer/reflector/dropper,
автоудаления, MCP и настройки отдельной модели памяти нет. Обычный блок не увеличен:
явный пакет источников передаётся только в намеренный ход разбора, не в постоянную вставку.

**Новое в 0.7.0 — поиск по источникам, меньше лишних записей и явные области памяти:**

- Поиск учитывает текст и ID записи, rationale, исходную цитату, путь источника и пути
  зависимостей. `Go`, `БД`, числа, `C#` и `C++` совпадают целыми токенами; у остальных слов
  остаётся эвристика окончаний. Score считает разные термины, не повторы цитаты. Внутри
  класса приоритетов sparse relevance учитывает информативность термина в текущем корпусе;
  затем идут coverage, свежесть, точные слова и ID. Старые версии и retired не искажают
  статистику. По той же релевантности выбираются seed для связанных оснований.
- До трёх свежих совпадений доставляют до шести zero-score соседей одним исходящим переходом
  по `dependsOn`/`links`. Обязательные записи, совпадения и открытая работа остаются впереди.
  Связь не принимает предложение, не снимает `STALE` и не меняет полномочия источника.
- `project_memory op=episodes id=<id> offset=<hit.offset>` возвращает дословную страницу.
  Следуйте `nextOffset` до `null`; без offset чтение начинается с 0. Это безопасные
  неотрицательные позиции UTF-16, которые не могут разрывать surrogate pair. Стандартная
  страница — 2400 единиц; `limit=<единицы>` задаёт от 200 до 12 000 на страницу. Роль и полная
  длина оригинала сохраняются.

- **Пересобираемый поиск истории.** Lazy FTS5 в `.memory/runtime/search.sqlite` хранит токены,
  не ещё одну стенограмму. Оригиналы остаются в `state.sqlite`; старый writer замечается.
  При сбое — явный degraded и полный streaming fallback. `/huimem index` показывает состояние,
  `/huimem index rebuild` пересобирает только производный индекс.
- **Меньше автоматического шума.** Несвязанные accepted-решения не заполняют каждый ход одним
  статусом. Обязательные правила, сильные совпадения и текущая работа сохраняют приоритет;
  явное чтение по ID остаётся, исправления и смена источников не замораживаются.
- **Курируемый Wiki/ADR.** `/huimem learn` намеренно запускает один обычный ход основной
  модели. `project_memory op=wiki` публикует, читает, перечисляет и проверяет производные
  страницы с точными версиями источников. Смена основания даёт STALE; страница не становится
  evidence и не принимает proposed-решение. `action=history path=<путь>` читает локальный Git,
  но сообщение коммита не считается доказанной причиной решения.
- **Project/session/personal.** Прежние вызовы остаются project. `scope=session` связан с
  native ID диалога и отделён от проекта. Personal выключен до человеческого
  `/huimem personal on` в активном профиле OMP; `scope=personal` переносит только выбранное
  исходное evidence, не полную проектную стенограмму.
- **Запись по изменению.** Идентичные retrieval receipts, подтверждённая проекция и
  неизменный checkpoint не вызывают повторных SQL-изменений. Новые изменения не скрываются.

Primary SQLite остаётся schema 2. MCP, сервер, embeddings и фоновая модель не добавлены.
Прежний **общий** предел — 9000 UTF-16 единиц, включая подписанные scoped-записи.
[Аудит исходников двадцати плагинов](../RETRIEVAL-RESEARCH.md) объясняет выбранные и
отклонённые механизмы. [Проверки](../VALIDATION.md) разделяют поиск, latency, совместимость
и реальные ответы модели, а не обещают решение всех возможных задач или лидерство.

**Новое в 0.6.10** — из той же тестовой сессии:

- **Правка документа памяти больше не устаревает запись, которая цитирует сообщение.** Обычная
  работа правит `.memory`, и каждая запись без `dependsOn` становилась STALE; единственным
  ответом было пересохранить их с тем же текстом — десять записей в замеренном проекте, четыре в
  тестовом, минута сорок четыре из шестиминутного хода. Сигнал, который снимают обрядом,
  перестаёт быть сигналом. Слова пользователя не меняются вместе с документом, поэтому такие
  записи не трогаются; файловый источник ведёт себя как прежде, явный `dependsOn` по-прежнему
  решает сам, а подмену сообщения всё так же ловят doctor и `op=evidence`. На записях тестового
  проекта: одна обычная правка `MEMORY.md` устаревала 7 из 7, теперь 0 из 7.
- **Отказ называет третью форму источника.** Цитируя мой ответ из прошлого хода, модель получила
  «скопируй дословную выдержку из текущего сообщения пользователя» — и ничего больше; путь найти
  то сообщение и сослаться на него через `origin="episode"` назван не был, и минута ушла на то,
  чтобы дойти до него самой.

**Новое в 0.6.9** — замерено на тестовом проекте, который вела модель с собственного сервера
вывода пользователя (`ai1/qwen38-flash-next`, контекст 131K), а не передовая модель:

- **Вопрос, который задают сейчас, опирается на запрос, оставивший пробел.** Сохраняя три
  вопроса, модель передала `source.origin="episode"` без `episode` — для вопроса в описании было
  сказано «источник — твоё собственное сообщение», а у вопроса, который задают сейчас,
  сохранённого сообщения ещё нет. Отказ при этом предлагал только `user` и `file`, и ни один
  вопросу не подходит. Теперь обычная форма — `origin="user"` с дословными словами запроса, по
  которым нельзя действовать; `origin="episode"` остаётся для вопроса, заданного в прошлом ходу;
  отказ называет все три формы.
- **Документ дизайна, который создаёт стартовый набор, входит в канонический набор.**
  `/huimem init` писал `.memory/DESIGN.md`, набор его не содержал, а блок называл свой перечень
  полным — та же нестыковка, которая в замеренном проекте потребовала ручного `/huimem include`,
  попадала в каждый новый проект. Init регистрирует файл, если создал его сам; проект с записями
  не трогается, потому что добавление документа один раз помечает записи без `dependsOn` STALE.

Эта же сессия — первое свидетельство, что операции 0.6.8 достижимы и без передовой модели: на
просьбу проверить цитату и прогнать диагностику модель с первого раза вызвала `op=evidence` и
`op=doctor` и своего SQL не писала.

**Новое в 0.6.8** — всё замерено на настоящем проекте (см. [проверки](../VALIDATION.md)):

- **Сверка цитаты без собственного SQL.** `op=evidence` знал только файлы, поэтому, чтобы сверить
  цитаты реестра с сохранёнными сообщениями, модель 17 раз открывала `state.sqlite` сама: главная
  проверка всей модели доказательств делалась снаружи плагина и в журнал не попадала. Теперь
  `evidence id=<запись>` сверяет запись с её источником, `evidence id=<эпизод> quote=<текст>`
  отвечает, есть ли цитата в том сообщении, а `evidence` без того и другого проверяет весь реестр
  и называет неподтверждённые записи. Каждая сверка пишется в журнал.
- **Блок называет записи, которые не поместились.** При 20 записях в блок попадали 7, а 13
  отбрасывались по бюджету на каждом из 43 ходов, и строка говорила лишь, что они есть; полный
  список ID был только в сгенерированном `RECORDS.md`. Теперь пропущенные названы со статусом, а
  `recall id=` принимает до десяти ID через запятую — именно это нужно для `expectedVersion`.
- **Предложенное решение — предложение.** «Proposed требует проверки» решение выполнить не может:
  его принимает только пользователь. В замеренной сессии два proposed-решения несли на себе 45 КБ
  архитектурного документа, а девять определяющих его вопросов были заданы в самом конце.
- **Вопрос, ждущий ответа, — это запись**: `kind=question`, `open | answered | dropped`. Те девять
  вопросов не существовали в памяти нигде — они выжили прозой в сводке чекпоинта и в документах,
  то есть там, где правила велят прозе не доверять. Открытый вопрос закреплён в блоке, пока не
  сохранён как `answered` со ссылками на записи, которые дал ответ; doctor называет открытые и
  предупреждает, когда ответ ничего не изменил.
- **Нумерованный ответ несёт свой вопрос.** `source.answers=<ID твоего сообщения>`: цитата
  «2. Это репозиторий» сама по себе не доказывает ничего, и связь модель восстанавливала рукой —
  в `MEMORY.md` и ADR, с пометкой, что это сопоставление.
- **Чекпоинт сохраняет следующий шаг.** До модели он доходил обрезанным до 218 символов из 780 —
  без той части, которая и говорит, что делать дальше. Теперь у сводки есть минимум места в блоке,
  а каждая её строка режется с двух концов с явной пометкой о пропуске.
- **Меньше шума и повторов.** Ход, отданный OMP дважды, — один эпизод, а не два ID одних и тех же
  слов; строка о подагенте пишется раз на запрос, а не на каждое обращение к модели, где она
  занимала 157 записей журнала из 169.

**С 0.6.7:** задание подагента записывается как сообщение ассистента, а не как слова пользователя
(девять из двадцати одного эпизода в замеренном проекте были заданиями), и подагент получает
сокращённый блок без правил сохранения (`subagentBlock: short | full | off`). Контракт записи
живёт в описании инструмента — до этого модель 34 раза ходила за ним в установленные исходники.
`project_memory op=doctor` даёт модели ту же диагностику только для чтения, что и `/huimem doctor`.
Поиск по эпизодам ранжирует совпадения, показывает совпавшую часть длинного сообщения, принимает
`role=user|assistant` и читает оригинал страницами по id (контракт выше). Канонический раздел — список файлов, а не их
текст; свои документы проект добавляет командой `/huimem include`. `CHECKPOINT_MISSING` —
предупреждение, а не ошибка, и однократные уведомления идут в журнал событий, который веер
подагентов не стирает (`/huimem context` его показывает).

**С 0.6.5:** обновление плагина теперь доходит до уже открытого разговора. База помечается
тем, кто в неё писал, и после обновления следующий блок памяти один раз сообщает, что изменилось в
правилах, — иначе возобновлённая сессия продолжает работать по правилам, которые видела на прошлых
ходах. Настройки сохраняют ключи, которых эта версия не знает, поэтому смена сборки в любую сторону
их больше не стирает. Пустой реестр назван одной строкой, а не выглядит как неудачный поиск. `/huimem` показывает
версию сборки и то, кто писал в базу; `/huimem doctor` сообщает о незавершённом переходе.

**С 0.6.4:** `/huimem off` и `/huimem on` выключают и включают память проекта, а правила
сохранения прямо говорят, что долгоживущие факты принадлежат реестру, а не рукописным файлам
`.memory`. **С 0.6.3:** `/huimem doctor` показывает устаревшие или потерянные основания, недоступные required-записи, ADR без «Основания» и расхождения задач. Команда открывает существующую базу только для чтения и ничего не исправляет. Подробнее — [диагностика](../GUIDE.md#doctor). Результаты проверки и последовавшие исправления — в [проверках](../VALIDATION.md).

Нужен OMP с настроенной основной моделью:

**mnemopi не требуется.** huimem использует собственную SQLite через среду OMP. `/huimem init` ставит проекту `memory.backend: off`; отдельные сервер и модель памяти не нужны.

**Читаемый реестр:** commit автоматически обновляет `.memory/RECORDS.md` — читаемый снимок реестра. `/huimem` показывает синхронизацию, `/huimem sync` повторяет публикацию без LLM. `/huimem context` показывает размер, хеш и ID/версии целиком вошедших записей последнего подготовленного блока; это не доказательство использования фактов моделью. Журнал хранит до 100 записей без копирования текстов фактов. Базы от v0.3.x и старше обновляются до схемы 2: перед переходом остановите OMP и сохраните копию `.memory`. Старые версии со схемой 1 не откроют обновлённую базу.

**Канонические документы (с 0.6.7):** набор — `MEMORY.md`, `PROJECT.md`, `todo.json`,
`architecture.json` и `.memory/adr/**`. `/huimem include <путь>` добавляет к нему другой документ
внутри `.memory`, `/huimem exclude` убирает, не больше десяти. Добавленный документ перечислен в
блоке, входит в хеш набора и отслеживается на устаревание. В замеренном проекте `.memory/DESIGN.md`
на 17 КБ был живым документом памяти вне набора, а блок при этом сообщал модели, что ничего другого
памятью проекта не является. Смена набора может устаревать файловые записи без `dependsOn`,
но не неизменяемые источники-сообщения. Generated RECORDS.md, Wiki и runtime не добавляются
в canonical set.

**Открытые вопросы (с 0.6.8):** вопрос, на который ждёшь ответа пользователя, — это запись с
`kind=question` и `status=open`: текст — сам вопрос, источник — твоё собственное сообщение.
Открытый вопрос закреплён в блоке рядом с текущей работой, поэтому «ждём ответа» едет вместе с
памятью, а не остаётся в разговоре. Повторное сохранение как `answered` со `links` на записи,
которые дал ответ, снимает закрепление; `dropped` закрывает вопрос без ответа. `project_memory
op=doctor` называет открытые вопросы и предупреждает об отвеченном, который ни на что не ссылается.
Когда пользователь отвечает номерами, `source.answers=<ID твоего сообщения с вопросом>` держит пару
вместе: цитата вида «2. Это репозиторий» сама по себе не доказывает ничего.

**Сверка доказательств (с 0.6.8):** `op=evidence` перепроверяет уже сохранённое. С `id=<запись>`
он сверяет запись с её источником — цитата на месте, файл не изменился, роль сообщения допустима
для принятого решения. С `id=<эпизод> quote=<текст>` отвечает, есть ли цитата в том сообщении, и
показывает совпавшую часть. Без того и другого проверяет все записи и перечисляет неподтверждённые.
Каждая сверка — расписка в журнале, чего самодельный скрипт по базе не даёт.

**Подагенты (с 0.6.7):** задание подагента пишет модель, поэтому оно записывается как сообщение
ассистента и не может стать пользовательским основанием принятого решения. В блоке подагента
остаются правила доказательств, список файлов и записи, а правила сохранения убраны; режим задаёт
`subagentBlock` в `.memory/settings.json`: `short` (по умолчанию), `full` или `off`.

**Старые ADR:** `/huimem adr-audit` показывает ADR без блока «Основание», которые можно перенести в контракт, и ничего не пишет. `/huimem adr-audit apply` вставляет в основание цитату пользователя из реестра, а все исходные строки сохраняет под заголовком «Интерпретация [?]», предварительно сделав побайтовую копию в `.memory/adr-backup/`. Документ переносится, только если его явно называет по пути ровно одно принятое решение, причина дословно входит в цитату, а сама цитата в момент переноса заново сверяется с сохранённым сообщением, которое должно существовать и принадлежать пользователю; иначе выводится `UNVERIFIED` и ничего не записывается. В v0.5.0 последней сверки не было: если вы запускали с ней `apply` на правленной, слитой или восстановленной базе, сравните каждое перенесённое основание с исходным сообщением. Связанные решения из разговора после этого помечаются STALE. В замере 20 на 20 с предрегистрацией у перенесённых документов не было явных приписываний, но превосходство над неперенесёнными статистически не доказано.

```sh
omp plugin install github:Clientik/omp-huimem#v0.8.3
```

> [!IMPORTANT]
> **Для начала работы один раз выполните в проекте.** Откройте `omp` в корне проекта и введите:
>
> ```text
> /huimem init
> ```
>
> До этого память выключена. Команда создаёт `.memory/`, `.omp/config.yml`, `.omp/RULES.md`,
> `AGENTS.md` и строки `.gitignore` из встроенного starter. Существующие файлы она не
> перезаписывает и перечисляет те, что оставила. Память работает со следующего сообщения:
> без перезапуска и без копирования.

Установка идёт на уровне пользователя. Без `/huimem init` project-память выключена: нет проектной БД, захвата стенограммы и project-контекста; обычный `project_memory` отвечает `PROJECT_MEMORY_NOT_ENABLED`. Отдельно разрешённая personal-память может работать и здесь, не создавая проектную `.memory`. Маркер проекта — `.memory/MEMORY.md`.

После `init` попросите агента использовать skill `initmem` для заполнения карты по реальному коду. Архитектурные запреты задайте под свой проект (`/huimem arch`); по умолчанию их нет.

**Статус установки:** установка из GitHub проверена целиком на Windows с OMP 18.1.5 и повторно с 18.11.0 — плагин установился, зарегистрировался и отработал живые сессии. Прямая загрузка тоже работает. Подробности и запасной способ — в [руководстве](../GUIDE.md).

**Экран настроек:** в терминале `/huimem` открывает экран из родных диалогов OMP. В каждой
строке видно текущее значение; Enter меняет его или выполняет действие, Esc закрывает. Там
можно выключить и включить память в этом проекте, поставить сохранение на паузу, задать
бюджет поиска и предел вставки, выбрать
обязательные записи из реестра, обновить `RECORDS.md`, посмотреть последний блок памяти,
перенести старые ADR и сбросить пределы. В проекте без памяти тот же экран предлагает её
включить. Значения хранятся по проекту в `.memory/settings.json`.

**Выключатель (с v0.6.4):** `/huimem off` отключает project/session: нет проектного блока,
записи сообщений и commit; `/huimem on` возвращает их. Данные сохраняются, состояние лежит
в `.memory/settings.json`. Personal отключается независимо: `/huimem personal off`.
`/huimem pause` блокирует commit/checkpoint, подтверждение разбора, Wiki publish и index
rebuild только в текущем процессе; чтение остаётся доступным. В режимах RPC и `-p`
`/huimem` выводит состояние текстом, а все действия доступны подкомандами (`/huimem help`).
`/huimem omp` перечисляет настройки OMP, влияющие на память: плагин их показывает, но чужой
конфиг не переписывает.
Выбрать `huimem` в `memory.backend` нельзя — в OMP это закрытый список, а API регистрации
бэкенда расширением нет. Расширение работает рядом с любым из них.

**Обязательные записи:** `/huimem require <id>` выдаёт запись в каждом ходе раньше
совпадений с вопросом, даже если вопрос о другом; `/huimem unrequire <id>` снимает отметку
(не больше 10). Список задаёт только пользователь: правку `.memory/settings.json` файловыми
инструментами плагин блокирует. Обязательные записи вместе занимают не больше половины
бюджета поиска. Более длинная показывается дословным началом цитаты с пометкой
`quoteClipped`. Если не помещается и оно, запись не выдаётся и называется в уведомлении
`REQUIRED records not shown in full`: её читают по ID, а место получают записи по вопросу, если помещаются.
Там же названы отсутствующие и снятые с действия ID. Уведомление не обрезается посреди ID:
длинный список заменяется числом, а `project_memory status` возвращает все обязательные ID.
Автоматический блок затем выбирает сильные совпадения, текущую работу и связанные основания,
но не закрепляет все несвязанные accepted-решения. Явный recall сохраняет широкий обзор.

**Объяснимое устаревание:** запись может перечислить, на что опирается: `dependsOn: [{id}]`
или `[{path}]`; код закрепляет текущую версию записи или хеш файла. Такая запись становится
STALE, только если основание изменилось, снято с действия или пропало, и причина видна
(`db changed: version 1 -> 2`), в том числе по цепочке записей. Независимые записи не
затрагиваются. STALE снимается только новой версией с текущими основаниями. Без `dependsOn`
источник-сообщение сохраняет своё evidence; файловые записи также учитывают смену канонических документов.

**Параллельные задачи:** сводка чекпоинта относится к задаче, если commit меняет ровно одну
запись задачи или передаёт `task=<id задачи>`. Тогда блок памяти перечисляет `Task checkpoints`
под ID каждой задачи, первой идёт совпавшая с запросом, и следующий шаг одной задачи не
выдаётся за шаг другой. Сводка без задачи показывается отдельно с временем;
`project_memory recall` по ID задачи возвращает её последний чекпоинт. Ветка git
записывается только для диагностики. Отдельный `git worktree` имеет свою `.memory/runtime`
и не видит записей основного каталога.

## Где что хранится

| Файл | Содержание |
| --- | --- |
| `.memory/MEMORY.md` | Актуальные факты и ограничения |
| `.memory/RECORDS.md` | Автоматический снимок реестра; не редактировать и не считать независимым доказательством |
| `.memory/adr/` | Решения и причины |
| `.memory/todo.json` | Задачи и их состояние |
| `.memory/PROJECT.md` | Карта кода и рабочие команды |
| `.memory/architecture.json` | Проверяемые архитектурные запреты |
| `.memory/DESIGN.md` | Договорённости о дизайне интерфейса |
| `.memory/runtime/state.sqlite` | Эпизоды, версии свидетельств и сводки |
| `.memory/runtime/search.sqlite` | Пересобираемый поисковый индекс; не evidence |
| `.memory/wiki/` | Производные Wiki/ADR со ссылками на записи; не canonical evidence |
| `.memory/runtime/scopes/<session hash>/` | Изолированные записи native-диалога |
| `.omp/RULES.md` | Короткие жёсткие требования, переприкрепляются рядом с текущим ходом |
| `AGENTS.md` | Фон и конвенции, выдаются один раз при открытии сессии |

В новом проекте две служебные папки: `.memory` и `.omp`. `AGENTS.md` и `.gitignore` — обычные файлы корня. Код установленного плагина хранится отдельно от данных проекта.

## Пример работы

Вы говорите: «Используем PostgreSQL, потому что нужны транзакции между заказами и оплатами».

Расширение сохраняет сообщение. Агент обновляет факты и решение, затем может записать свидетельство в реестр. В новой сессии расширение передаёт краткий контекст, чтобы агент мог восстановить выбор и причину.

Если решение изменилось, агент исправляет документы и создаёт новую версию записи. При противоречии нужно проверить первоисточник: старая цитата сама по себе не делает старое решение актуальным.

**Запись истории автоматическая; выделение важных знаний зависит от основной модели.** Второй LLM-процесс не запускается.

## Разработка и лицензии

С установленным Bun: `bun run build` собирает расширение, `bun run check` запускает тесты и проверку пакета. Актуальные результаты — в VALIDATION.md. Дополнительные runtime npm-зависимости не нужны. Сборка включена в репозиторий.

Код и семь bundled skills распространяются с [MIT-лицензиями](../../THIRD_PARTY_NOTICES.md). Поле `private` в package.json предотвращает случайную публикацию в npm и не мешает распространению через GitHub.
