**Память проекта для [oh-my-pi (OMP)](https://github.com/can1357/oh-my-pi): что решили, почему, где искать и что осталось сделать.**

После перезапуска агент получает сохранённые знания о проекте. Текущее состояние лежит в читаемых файлах, история и свидетельства — в локальной SQLite. Расширение помогает отличать подтверждённые решения от предположений и замечать устаревшие записи.

Один плагин. Без отдельного сервера, embeddings и фоновой нейросети. Работает с основной моделью OMP, в том числе локальной.

> **Предварительная версия 0.4.0.** Проверена с OMP 18.1.5. Обычный Pi пока не поддерживается. Плагин помогает уменьшить потерю контекста; отсутствие галлюцинаций не гарантирует.

## Для кого

Для разработчиков, которые ведут проект с ИИ и не хотят в каждой сессии заново объяснять архитектуру. Особенно полезно, если основная локальная модель занимает доступные ресурсы и запускать дополнительную модель ради памяти неудобно.

## Что даёт

- **Знания рядом с кодом.** Факты, решения и задачи можно открыть, исправить и хранить в Git.
- **Источник у записи.** Реестр проверяет цитату пользователя или содержимое файла. ID сообщения и хеш вычисляет код.
- **Историю исправлений.** Новое решение получает следующую версию записи. Старое остаётся в истории.
- **Видимое устаревание.** Изменился источник или основные документы — запись получает `STALE` и требует проверки.
- **Ограниченный контекст.** Расширение передаёт блок до 8000 символов, а не весь архив. Полные источники агент читает по необходимости.

## Установка

Нужен OMP с настроенной основной моделью:

**mnemopi не требуется.** huimem использует собственную SQLite через среду OMP. Сохраните `memory.backend: off` из starter; отдельные сервер и модель памяти не нужны.

**В рабочей версии:** commit автоматически обновляет `.memory/RECORDS.md` — читаемый снимок реестра. `/huimem` показывает синхронизацию, `/huimem sync` повторяет публикацию без LLM. `/huimem context` показывает размер, хеш и ID/версии целиком вошедших записей последнего подготовленного блока; это не доказательство использования фактов моделью. Журнал хранит до 100 записей без копирования текстов фактов. Эти изменения ещё не входят в релиз v0.4.0. База обновляется до схемы 2: перед переходом остановите OMP и сохраните копию `.memory`. Старые версии со схемой 1 не откроют обновлённую базу.

```sh
omp plugin install github:Clientik/omp-huimem#v0.4.0
```

Установка идёт на уровне пользователя, поэтому расширение загружается во всех проектах. **Память включается только там, где вы её развернули:** без `.memory/MEMORY.md` расширение бездействует — не создаёт базу, не добавляет контекст, не выдаёт предупреждений, а `project_memory` отвечает `PROJECT_MEMORY_NOT_ENABLED`. Чужие репозитории остаются нетронутыми, и в них не появляется файл базы, не закрытый вашим `.gitignore`.

Один раз скопируйте **содержимое `starter/`** из репозитория в корень нового проекта. В существующем проекте объедините файлы с текущими настройками. Память заработает со следующего сообщения, перезапуск OMP не нужен. Запустите `omp` из корня и выполните:

```text
/project-memory-status
```

Попросите агента использовать skill `initmem` для заполнения карты по реальному коду. Архитектурные запреты задайте под свой проект.

**Статус установки:** установка из GitHub проверена целиком на Windows с OMP 18.1.5 — плагин установился, зарегистрировался и отработал живые сессии. Прямая загрузка тоже работает. Подробности и запасной способ — в [руководстве](../GUIDE.md).

`/huimem` показывает состояние памяти текущего проекта и меняет бюджет поиска и предел
вставки в контекст; значения лежат в `.memory/settings.json`. `/huimem omp` перечисляет
настройки OMP, влияющие на память: плагин их показывает, но чужой конфиг не переписывает.
Выбрать `huimem` в `memory.backend` нельзя — в OMP это закрытый список, а API регистрации
бэкенда расширением нет. Расширение работает рядом с любым из них.

## Где что хранится

| Файл | Содержание |
| --- | --- |
| `.memory/MEMORY.md` | Актуальные факты и ограничения |
| `.memory/RECORDS.md` | Автоматический снимок реестра; не редактировать и не считать независимым доказательством (рабочая версия) |
| `.memory/adr/` | Решения и причины |
| `.memory/todo.json` | Задачи и их состояние |
| `.memory/PROJECT.md` | Карта кода и рабочие команды |
| `.memory/architecture.json` | Проверяемые архитектурные запреты |
| `.memory/DESIGN.md` | Договорённости о дизайне интерфейса |
| `.memory/runtime/state.sqlite` | Эпизоды, версии свидетельств и сводки |
| `.omp/RULES.md` | Короткие жёсткие требования, переприкрепляются рядом с текущим ходом |
| `AGENTS.md` | Фон и конвенции, выдаются один раз при открытии сессии |

В новом проекте две служебные папки: `.memory` и `.omp`. `AGENTS.md` и `.gitignore` — обычные файлы корня. Код установленного плагина хранится отдельно от данных проекта.

## Пример работы

Вы говорите: «Используем PostgreSQL, потому что нужны транзакции между заказами и оплатами».

Расширение сохраняет сообщение. Агент обновляет факты и решение, затем может записать свидетельство в реестр. В новой сессии расширение передаёт краткий контекст, чтобы агент мог восстановить выбор и причину.

Если решение изменилось, агент исправляет документы и создаёт новую версию записи. При противоречии нужно проверить первоисточник: старая цитата сама по себе не делает старое решение актуальным.

**Запись истории автоматическая; выделение важных знаний зависит от основной модели.** Второй LLM-процесс не запускается.

## Разработка и лицензии

С установленным Bun: `bun run build` собирает расширение, `bun run check` запускает тесты и проверку пакета. Актуальные результаты — в VALIDATION.md. Дополнительные runtime npm-зависимости не нужны. Сборка включена в репозиторий.

Код и семь bundled skills распространяются с [MIT-лицензиями](../../THIRD_PARTY_NOTICES.md). Поле `private` в package.json предотвращает случайную публикацию в npm и не мешает распространению через GitHub.
